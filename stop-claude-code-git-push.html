How to stop Claude Code from pushing without you

Refuse it, ask every time, or hold it for later. What each one does in manual, auto and skip-permissions mode, and a backstop that lives on the server.

Checked against Claude Code's permission and hooks docs on 2026-10-28.

Short version: a deny rule refuses git push in every mode, skip-permissions included. If you want the push to happen later, once you've looked, hold it with a PreToolUse hook instead, so the run keeps going. Either way, protect your main branch on the server, and make sure the credentials on the agent's machine can't change repo settings.

Sources: permission modes ("Deny rules block in every mode, including bypassPermissions"; auto mode allows "pushing to any branch of the repository you're working in"; explicit ask rules still prompt in manual, auto and skip-permissions mode) and the hooks guide (PreToolUse hooks fire before the permission check, in every permission mode). One exception to all of this: a mod you've installed can approve an action itself, when there are no managed settings and no Team or Enterprise login.

1. Refuse it: a deny rule

In .claude/settings.json (shared with your team) or .claude/settings.local.json (just you):

{
  "permissions": {
    "deny": ["Bash(git push *)"]
  }
}

Deny rules are checked first, before ask and allow rules, and an allow rule can't carve an exception out of one. The agent is told the command was refused. Good for "never, in this project". Not so good for overnight work you do want shipped: the push can't happen until you edit the rule, and an agent that's been refused may try to finish the task another way.

2. Ask every time: an ask rule

{
  "permissions": {
    "ask": ["Bash(git push *)"]
  }
}

You get a prompt for each push, even if you've allowed git commands more broadly. Fine at the keyboard, and with Remote Control the prompt reaches your phone. The cost: the whole run waits at the prompt until you answer.

3. Hold it for later: a PreToolUse hook

A hook can refuse the command for now, tell the agent it's queued, and let it carry on. Two ways to get that:

  • Write it yourself. Our overnight guide has a short, tested hook that holds git push and logs it. In the morning you run what you approve yourself.
  • Use the free plugin. Agent Mission Control holds git push, npm publish, rm -rf and more by default, as a1, a2. /mc approve a1 runs exactly that command, once, and you can send it remotely over Remote Control.
# in Claude Code, one line at a time
/plugin marketplace add long-run-labs/agent-mission-control
/plugin install agent-mission-control@long-run-labs
/mc goal Ship the CSV export --done-when tests pass and a PR is open

Every pattern has gaps

Rules and hooks match the command's text, so a push written another way can slip past. The docs' own example: Bash(git push *) matches git push origin main but not git -C . push origin main or git 'push' origin main. The plugin's patterns have the same limit; a pattern like git*push catches more variants, and holds a few harmless commands too.

So add a backstop that doesn't live on the agent's machine:

  • Protect the branch on the server. On GitHub, a ruleset on main that requires a pull request, with an empty bypass list, means no push lands there directly. With a classic branch protection rule, also turn on Do not allow bypassing the above settings: by default, admins can bypass it, and on a personal repo your own token is an admin's.
  • Keep admin credentials off the agent's machine. A token that can change repo settings can also remove the protection. Give the agent a fine-grained token without the Administration permission, and its own branch, if your setup allows it.

Then the local rule is a seatbelt, and the server rule is the backstop.
